# 用 Instatic 维护网站 — 演示文档

> 面向：参与网站日常维护的编辑人员与相关负责人
> 场景：以 DITE 站点为实例（在线地址：<https://mateng-cb.github.io/instatic-demo/>）

---

## 一、Instatic 是什么

Instatic 是一个**自托管的开源内容管理系统（CMS）**，自带可视化网页编辑器：

- 维护人员用浏览器打开管理后台，**所见即所得**地编辑网页；
- 改动实时保存为草稿，点「发布」后才对外可见；
- 发布产物是**纯静态 HTML + 干净 CSS**——没有框架运行时、加载快、SEO 友好，可以托管在任何静态空间（GitHub Pages、对象存储、自有服务器均可）。

一句话：**像改文档一样改网站，发布出去的是一个又快又轻的静态站点。**

---

## 二、日常维护的操作入口

### 1. 打开管理后台

- 服务器由管理员负责运行（本地或容器部署），维护人员**只需要浏览器**；
- 访问 `https://<服务器地址>/admin`，用账号登录；
- 登录后进入 Dashboard（仪表盘），左侧导航切换各个工作区。

### 2. 工作区总览

| 工作区 | 地址 | 用来做什么 |
|---|---|---|
| **Dashboard** | `/admin` | 总览入口 |
| **Site 编辑器** | `/admin/site` | 可视化编辑网页（最常用） |
| **Content** | `/admin/content` | 管理文章/新闻类内容集合 |
| **Media** | `/admin/media` | 管理全站文件（图片等） |
| **Data** | `/admin/data` | 查看底层数据表（高级） |
| **AI** | — | 内置 AI 助手（可选功能） |

### 3. 保存与发布的机制（重要）

- **没有「保存」按钮**：编辑器里的每次改动都实时写入服务器数据库，不存在忘保存丢稿的问题；
- **草稿与线上分离**：没点发布之前，公众访问到的仍是上一个已发布版本；
- **撤销**：编辑器内支持撤销（Undo），多人同时编辑时各自有独立的撤销历史；
- **多人协同**：多人可以同时编辑同一页面，改动实时同步、互不覆盖。

## 三、可以维护哪些内容

| 内容类别 | 具体能力 |
|---|---|
| **页面结构** | 新增 / 删除 / 重命名页面，调整层级，切换主页 |
| **页面内容** | 文字（双击直接改）、图片（自动生成多尺寸响应式变体）、按钮、容器布局、各类功能模块 |
| **可复用组件** | Visual Components（可视化组件）+ 插槽机制：一处定义、多处复用 |
| **全站页头页脚** | 模板（Templates）机制：页头、页脚改一次，全站生效 |
| **全站设计** | 颜色、字体（含 Google Fonts）、排版、间距的统一令牌管理 |
| **响应式适配** | 按断点（桌面 / 平板 / 手机）单独微调任意元素 |
| **文章类内容** | Content 工作区管理新闻、公告等集合，富文本编辑，Markdown 存储 |
| **媒体文件** | Media 工作区：文件夹管理、批量上传、使用情况追踪 |
| **代码级修改** | 内置代码编辑器（CodeMirror），可直改 HTML/CSS |

## 四、如何维护 — 分场景操作指南

### 场景 A：改文字、换图片（最常见）

1. 进入 **Site 编辑器**，在左侧站点树中选择页面；
2. 画布中**双击**文字直接修改，点击图片在右侧属性面板更换；
3. 无需保存——改动已实时入库存为草稿；
4. 点工具栏 **Publish → Publish**，几秒后线上生效。

### 场景 B：新增或调整页面

1. 站点树右键 / 工具栏操作：新增页面、拖拽调整层级顺序；
2. 从**模块插入器**拖入文字、图片、按钮、容器等模块拼装页面；
3. 也可从**已保存布局**一键套用之前存好的页面骨架；
4. 发布即可上线；可设为主页或调整路由。

### 场景 C：调整全站设计

1. 右侧面板进入颜色 / 字体 / 排版设置；
2. 修改的是设计令牌（Token）——改一处，引用该令牌的全站元素统一变化；
3. 预览确认后发布。

### 场景 D：发一篇新闻 / 公告

1. 进入 **Content 工作区**，左侧选集合（如「新闻」）；
2. 新建条目，富文本编辑正文，右侧设置发布属性；
3. 保存后，引用该集合的页面（列表页、详情页）自动更新。

### 场景 E：发布到线上（三种通道）

| 通道 | 操作 | 适用场景 |
|---|---|---|
| **站内发布** | 工具栏 Publish | 服务器直接对外提供服务 |
| **导出静态包** | Publish 菜单 → Export static site | 下载 zip，人工部署到任意静态空间 |
| **发布到 GitHub Pages** | Publish 菜单 → Publish to GitHub | 自动推送到 GitHub 仓库，Pages 托管，**零服务器成本** |

**Publish to GitHub 的操作**（本次演示重点）：

1. 首次使用在对话框里配置：仓库地址、分支、Base path、个人访问令牌（PAT）——配置会保存，之后**一键发布**；
2. 可填写本次**提交摘要**（如「更新首页合作伙伴」），留空则默认 `Publish site from Instatic`；
3. 点击 Publish 后可看到**实时上传进度**（第几个文件 / 共几个 / 当前文件名）；
4. 完成后提示 commit 链接，约一分钟内 GitHub Pages 生效。

## 五、优缺点评估

### 优点

1. **上手门槛低**——可视化编辑，非开发人员即可维护；双击改字、拖拽排版；
2. **数据完全自控**——自托管，内容存在自己的数据库（SQLite / PostgreSQL），随时备份迁移，无供应商锁定；
3. **发布产物极轻**——纯静态 HTML + 手写 CSS，无框架运行时：加载快、SEO 好、安全面小；
4. **托管零成本可选**——GitHub Pages 通道不需要自己维护线上服务器；
5. **多人实时协同**——团队同时编辑，改动实时同步；
6. **权限与安全完善**——细粒度能力授权、发布等敏感操作需二次认证、支持 MFA、有审计日志；
7. **图片自动响应式**——上传一张原图自动生成多档宽度变体，页面按设备加载合适的尺寸；
8. **可持续扩展**——插件系统、AI 助手、外部工具（MCP）接入能力。

### 缺点 / 限制（需要知悉）

1. **需要自建服务端**——编辑后台依赖自己运行的服务器（部署、备份、升级是运维成本；仅静态托管通道可免）；
2. **静态通道不支持动态功能**——导出包 / GitHub Pages 是纯静态：表单降级为静态提示，按访客个性化的内容不可用（导出时会给出明确警告清单）；
3. **每次 GitHub 发布为全量推送**——大站点（如本站 900+ 文件，含全部响应式图片变体）每次上传需数分钟；无增量推送；
4. **令牌需要管理**——GitHub PAT 有有效期，到期后需在 GitHub 重新生成并在设置中更新，否则发布会失败；
5. **产品处于快速迭代期**——功能与接口更新较快，升级需跟随官方迁移流程；外部导入的存量页面中部分复杂交互需人工核对；
6. **生态尚小**——插件市场、社区资料、第三方支持还比较有限。

## 七、常见问题（Q&A 预案）

**Q：改错了怎么办？**
编辑器内直接撤销；若错误版本已发布，改回正确内容再发布一次即可（发布历史有 commit 记录可查）。

**Q：多人同时改一个页面会冲突吗？**
不会。实时协同引擎保证各编辑者的改动自动合并、互不覆盖。

**Q：我们的数据存在哪里？**
自己服务器的数据库里（SQLite 文件或 PostgreSQL），随时可整站备份、迁移，也可导出静态包脱离系统长期留存。

**Q：静态网站上表单还能用吗？**
静态通道中表单会降级为静态提示（导出报告会逐项警告）；需要完整动态能力的表单请走站内发布通道。

**Q：为什么上传显示 900+ 个文件？**
站点引用到的每张图片会带上多档宽度的响应式变体（按访问设备加载最合适的一档），属于正常现象，无需人工管理。

**Q：GitHub 令牌过期了会怎样？**
发布会明确报错提示；到 GitHub 重新生成 PAT，在发布设置里更新即可恢复，站点本身不受影响。

## 八、演示会议问题与解决方案

### 问题 1：运营维护过的版本，开发时如何同步？

**结论：内容与代码分层同步——内容走「站点传输」，代码走 Git。**

Instatic 的**内容全部存在数据库里**（页面树、文章、媒体库），代码只决定功能——两层天然分离，各走各的同步通道：

| 层 | 同步方式 | 操作 |
|---|---|---|
| **内容层**（运营改的页面/文章/图片） | **站点传输（Site Transfer）** | 运营实例：Data 工作区 → Export site，导出完整站点包（含全部数据表、内容条目、媒体库、跳转规则）；开发实例导入后得到**完全一致**的站点 |
| **代码层**（开发改的功能） | **Git 分支 + PR** | 开发分支合并到 main，部署拉取更新；数据库内容不受代码升级影响 |

**标准流程**：开始一轮开发前，先从运营环境导出站点包导入开发环境（拿到最新内容基线）→ 开发验证 → 代码走 PR 合并 → 如开发期间也调整了内容，再反向导出站点包推回运营环境。站点包同时也是**整站备份**手段。

### 问题 2：不同人员维护之间版本如何同步？

**结论：同一实例上的多人维护是实时自动同步的，不存在「版本合并」问题。**

- **同一站点（推荐模式）**：所有维护人员登录同一个后台，基于实时协同引擎（Yjs CRDT）——多人同时编辑同一页面，改动**实时合并、互不覆盖**，每个人始终看到别人的最新修改，无需刷新、无需手动合并；
- **跨实例**（如两地各有独立部署）：用问题 1 的站点传输定期对齐内容。

### 问题 3：打包后文件结构变动，URL 路径如何保持（如 `2026Beijing/index.html`）？

**结论：静态导出按「目录式路由」落盘，URL 结构原样保持。**

导出规则：

| 线上 URL | 导出包内路径 |
|---|---|
| `/` | `index.html` |
| `/2026Beijing/` | `2026Beijing/index.html` |
| `/foo/bar/` | `foo/bar/index.html` |

即每个页面对应一个同名目录 + `index.html`，`2026Beijing` 这类栏目的 URL 在打包后**完全不变**。托管到 GitHub Pages 项目站点（形如 `用户名.github.io/仓库名/`）时，只需在发布设置里填 **Base path**（如 `/instatic-demo`），页面内部所有链接、样式、图片引用会**自动统一加上前缀**，不需要逐个修改。

### 问题 4：图片上传有无限制提示？

**结论：有明确的限制与拦截。**

- **单文件大小**：上限 **15 MB**（10 MB 以上会先给出「大文件」提醒），超限上传被拒并提示；
- **格式白名单**（按文件**真实内容检测**，不是只看扩展名，杜绝伪装文件）：
  - 图片：JPEG、PNG、GIF、WebP、SVG
  - 视频：MP4、WebM
  - 字体：woff / woff2 / ttf / otf
- 不支持的格式上传时会被拒绝并给出明确的错误提示。

### 问题 5：图片格式是否自动转 WebP？

**结论：是——上传后自动处理，且不只是格式转换。**

图片上传后系统自动执行完整的优化管线：

1. **自动生成响应式阶梯变体**：宽度 64 / 320 / 640 / 1024 / 1600 / 2048 六档，**全部编码为 WebP**；
2. 顶档输出**全质量 WebP**——访客浏览器永远不需要下载原始大图；
3. 同时生成**模糊占位图**（blurhash），图片加载前先显示模糊轮廓，视觉体验平滑；
4. 页面按访问设备自动挑选最合适的一档加载（手机不下载桌面大图）。

也就是说：维护人员上传什么格式的原图都可以（JPEG/PNG 均可），线上自动就是体积最优的 WebP，无需人工处理。

### 问题 6：导航栏栏目如何新增或修改？

**结论：导航栏是页面里的普通模块，可视化直接改；推荐收敛到全站模板统一管理。**

**修改现有栏目**：

1. Site 编辑器打开任意含导航的页面，点击选中导航栏中的栏目；
2. **双击**栏目文字直接改名；
3. 右侧属性面板修改**链接指向**（选择站内已有页面，或填外部 URL）。

**新增栏目**：

1. 先在左侧站点树中创建目标页面（栏目要链到它）；
2. 回到导航栏，选中一个现有栏目，复制一份；
3. 改栏目文字 + 把链接指向新页面，发布生效。

**最佳实践（推荐逐步落地）**：把导航栏放入**全站模板**（everywhere 布局，即全站统一的页头）或做成**可视化组件（Visual Component）**——这样导航**改一处、全站所有页面同步生效**，不必逐页修改。DITE 站点当前由静态站导入，若导航在多个页面重复出现，建议按上述方式收敛一次，后续维护就只改一处。

### 问题 7：支持文件夹概念吗？导入的页面可以按文件夹分类吗？

**结论：支持。站点资源管理器和媒体库各有一套完整的文件夹体系，导入的页面可以拖入文件夹分类。**

**① 站点资源管理器（Site Explorer，左侧站点树）**：

- 左侧树分为**五个分区：页面、模板、组件、样式、脚本**，每个分区都支持建**文件夹**分组，文件夹可嵌套、可展开/收起（状态会被记住）、可整体拖动；
- **文件夹是纯组织层，不影响 URL**：页面放进哪个文件夹、挪动文件夹，路由地址都不变——分类只为维护时好找，与线上路径无关；
- **导入的页面**（静态站导入 / 站点包导入）出现在页面分区后，**直接拖入文件夹**即可分类；静态导入不会按原站目录自动建文件夹，导入后手动建好文件夹、批量拖入一次即可；
- 通过站点包（Site Transfer）迁移时，文件夹组织结构随站点一起带走，新环境里分类不丢。

**② 媒体库（Media 工作区）**：

- 独立的文件夹体系：左侧文件夹树导航，画布式文件管理器里**文件夹和文件同屏**，支持嵌套文件夹；
- 图片/文件可**拖拽移入文件夹**（符合桌面文件管理器操作习惯）；
- 一个文件只属于一个文件夹；从站点包导入时**媒体文件夹结构原样保留**。

## 九、注意事项

- 账号、密码、个人访问令牌（PAT）**只保存在服务器设置中，不要在文档、聊天、截图中传播**；
- 发布属于敏感操作，系统会要求二次认证，这是预期行为；
- 大版本升级前请先整站备份数据库（管理员操作）。
